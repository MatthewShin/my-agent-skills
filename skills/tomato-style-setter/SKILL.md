# UI 디자인 디렉션 설계

사용자의 모호한 시각 요구를 검토 가능한 디자인 결정으로 바꾸고, 승인된 결정만 제품 UI에 일관되게 적용한다.

## 기본 원칙

- 프로젝트 지침과 기존 브랜드·디자인 시스템·컴포넌트를 먼저 따른다.
- 접근성, 정보 위계, 상태 식별성, 사용성을 장식 효과보다 우선한다.
- 하나의 스타일을 주 방향으로 삼고 다른 스타일은 목적이 분명한 특징만 보조적으로 사용한다.
- 스타일 프리셋과 색상 팔레트를 분리한다. 스타일은 표현 규칙을, 팔레트는 브랜드와 감성 역할을 정의한다.
- 사용자 승인 전에는 제품 코드와 기존 디자인 자산을 변경하지 않는다.
- 새 프레임워크나 디자인 시스템 도구를 임의로 도입하지 않는다.

## 1. 현재 상태 파악

먼저 저장소와 제공 자료에서 다음 정보를 확인한다.

- 제품 목적, 핵심 사용자, 플랫폼, 주요 작업과 대표 화면
- 기존 로고, 브랜드 컬러, 폰트, 디자인 토큰, 컴포넌트, 디자인 문서
- 기술 스택, 반응형 범위, 접근성 기준, 프로젝트별 제약
- 사용자가 원하는 감성, 참고 사례, 반드시 포함하거나 피할 요소

환경에서 확인할 수 없는 정보 중 결과를 바꾸는 항목만 묶어서 질문한다. 충분한 정보가 있으면 질문을 반복하지 않는다.

## 2. 스타일 방향 제안

사용자가 스타일을 지정하지 않았다면 [스타일 프리셋](references/style-presets.md)을 읽고 적합한 후보 2~3개를 제안한다. 후보마다 다음을 짧게 비교한다.

- 제품과 사용자에게 적합한 이유
- 핵심 시각 특성
- 사용성·접근성·성능 위험
- 주 스타일 또는 보조 스타일로서의 역할

가장 적합한 후보를 추천하되 사용자가 최종 선택하도록 한다. 사용자가 이미 스타일을 명시했다면 선택 단계를 생략하고, 위험하거나 상충하는 부분만 알린다.

선택 결과를 다음 형태로 고정한다.

- 주 스타일: 전체 표면, 형태, 위계, 상호작용의 기준
- 보조 스타일: 최대 하나, 적용할 특징과 범위를 명시
- 제외 규칙: 과도한 혼합을 막기 위해 사용하지 않을 특징

## 3. 톤앤매너 정의

다음 결정을 구체적인 디자인 언어로 작성한다.

1. 핵심 감성 키워드 3개와 피해야 할 키워드 2개를 정한다.
2. 표면, 깊이, 테두리, 질감, 아이콘, 이미지, 데이터 시각화, 모션 원칙을 정한다.
3. 기존 브랜드 컬러를 우선해 팔레트를 만든다. 브랜드가 없으면 [컬러 분위기 프리셋](references/style-presets.md#컬러-분위기-프리셋)을 출발점으로 삼는다.
4. 색상을 `primary`, `secondary`, `accent`, `canvas`, `surface`, `text`, `border`, `success`, `warning`, `error`의 의미 역할로 정의한다.
5. 본문 가독성, UI 경계, 포커스, 오류와 선택 상태가 색상 하나에만 의존하지 않도록 검토한다.
6. 기존 또는 시스템 폰트를 우선하고, 글꼴 라이선스와 다운로드가 필요하면 먼저 사용자에게 알린다.

색상 값만 나열하지 말고 각 역할, 사용 비율, 조합 금지 사항을 함께 설명한다. `canvas`·`surface`·neutral이 화면 대부분을 차지하고 `primary`는 주요 행동과 선택에, `accent`는 가장 제한적인 강조에 쓰이게 한다. 맥락 없이 고정 비율을 강제하지 않는다.

정확한 색상값을 제안하면 사용 가능한 계산 도구로 주요 텍스트·표면·UI 경계 조합의 대비를 확인한다. 확인하지 못한 값은 후보라고 표시하고 접근성 기준을 충족한다고 단정하지 않는다.

## 4. 최소 디자인 시스템 설계

요청된 대표 화면을 일관되게 만드는 데 필요한 최소 범위만 정의한다.

- Foundations: 컬러, 타이포그래피, 간격, 반경, 테두리, 그림자, 투명도, 모션
- Atoms: 텍스트, 아이콘, 버튼, 입력, 배지처럼 독립적으로 쓰이는 요소
- Molecules: 폼 필드, 검색, 카드 헤더처럼 atoms가 결합된 반복 패턴
- Organisms: 대표 화면 검토에 필요한 내비게이션, 카드 목록, 폼 영역 등 최소 조합

각 상호작용 컴포넌트에 필요한 `default`, `hover`, `focus`, `active`, `disabled`, `error` 상태를 정의한다. Atomic Design 용어를 코드 구조나 파일명에 강제하지 말고 프로젝트의 기존 관례에 매핑한다.

## 5. 리뷰 패키지 제시

[리뷰 템플릿](references/review-template.md)을 읽고 디자인 디렉션 명세와 대표 샘플을 제시한다.

대표 샘플에는 최소한 컬러, 타이포그래피, 버튼, 입력, 카드와 대표 화면 한 개의 방향을 포함한다. 제품 코드를 변경하지 않는 가장 작은 검토 수단을 선택한다. 환경이 지원하면 격리된 style tile이나 임시 미리보기를 만들고, 그렇지 않으면 구조화된 명세와 상태 예시를 제공한다.

명시적으로 다음 중 하나를 요청한다.

- 승인: 현재 방향으로 구현
- 부분 수정: 지정 항목만 바꾸고 다시 리뷰
- 방향 변경: 스타일 후보 단계로 돌아가기

승인 전에는 구현 단계로 넘어가지 않는다.

## 6. 승인된 방향 적용

승인 후 다시 현재 diff와 프로젝트 구조를 확인하고 다음 순서로 적용한다.

1. 기존 토큰과 컴포넌트로 표현할 수 있는 부분을 재사용한다.
2. 부족한 의미 토큰만 프로젝트 방식에 맞춰 추가한다.
3. 기초 요소부터 조합 요소 순으로 최소 변경한다.
4. 사용자가 요청한 화면과 컴포넌트 범위를 넘기지 않는다.
5. 기존 디자인 문서 위치를 따르고, 위치가 없으면 승인된 명세를 `docs/design-system.md`에 기록한다.

승인된 명세와 실제 구현이 달라져야 한다면 임의로 결정하지 말고 차이와 이유를 먼저 알린다.

## 7. 검증 및 보고

- 반응형 크기와 긴 텍스트에서 레이아웃을 확인한다.
- 키보드 포커스, 상태 식별, 텍스트·UI 대비, 모션 감소 환경을 확인한다.
- 색상·간격·타이포그래피가 토큰을 재사용하는지 확인한다.
- 사용자가 이미 실행한 검증 환경이 있고 프로젝트 규칙이 허용할 때만 headless 화면 검증을 사용한다.
- 개발 서버나 브라우저를 자동으로 실행하지 않는다.
- 변경 내용, 검증 결과, 남은 시각적 판단 항목을 짧게 보고한다.
