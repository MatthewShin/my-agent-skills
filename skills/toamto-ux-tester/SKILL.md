# 사용자 흐름 최적화

사용자의 실제 목적 달성 과정을 기준으로 서비스를 점검하고, 근거가 있는 최소 변경을 적용한 뒤 개선 효과를 같은 기준으로 재평가한다.

## 기본 원칙

- 시작 전에 반드시 테스트 방향과 목적을 수집한다.
- 화면의 미관보다 사용자의 목적 달성 여부와 막힘 지점을 먼저 판단한다.
- 실제 사용자 관찰, 실행 화면 관찰, 코드 검사, 휴리스틱 추론을 구분해 기록한다.
- 실제 end user가 참여하지 않았다면 휴리스틱 평가를 사용자 테스트 결과처럼 표현하지 않는다.
- 기존 디자인 시스템과 프로젝트 규칙을 우선하고 범위를 벗어난 재설계를 하지 않는다.
- 근거 없이 점수를 높이거나 개선 효과를 단정하지 않는다.
- 초기 평가 보고서를 먼저 제공하고 사용자가 개선 진행을 승인하기 전에는 제품 코드를 수정하지 않는다.
- 테스트 데이터, 계정, 토큰, 개인정보를 보고서나 저장소에 남기지 않는다.
- 개발 서버와 브라우저를 자동으로 실행하지 않는다.

## 1. 테스트 방향과 목적 수집

검사를 시작하기 전에 환경에서 확인할 수 없는 다음 정보를 사용자에게 묶어서 질문한다.

- 대상 서비스·화면과 테스트 범위
- 핵심 사용자 또는 역할과 숙련도
- 사용자가 달성하려는 주요 목적과 성공 조건
- 우선 검증할 flow, 기기, viewport, 입력 방식
- 알려진 문제, 변경 가능 범위, 제외 범위
- 실행 환경 또는 제공 가능한 화면·스크린샷·테스트 데이터

비밀번호나 실제 개인정보를 요청하지 않는다. 인증이 필요하면 사용자가 관리하는 테스트 세션이나 안전한 테스트 계정을 사용하도록 안내한다.

수집 결과를 `대상 사용자 / 핵심 목적 / 성공 조건 / 범위 / 증거 방식`으로 요약하고 사용자 의도와 맞는지 확인한다. 이미 명확히 제공된 항목은 다시 묻지 않는다.

## 2. 대상과 주요 flow 파악

프로젝트 지침과 현재 변경 상태를 읽고, 기존 정보 구조·라우트·컴포넌트·디자인 토큰을 확인한다. 사용자가 이미 실행한 서비스가 있고 프로젝트 규칙이 허용할 때만 사용 가능한 화면 검사 수단으로 관찰한다.

각 핵심 flow를 다음 형태로 정의한다.

- 시작 조건과 진입점
- 사용자의 목표
- 주요 단계와 분기
- 성공 상태
- 실패·취소·재시도 경로

각 단계마다 다음 질문을 적용한다.

1. 사용자는 여기서 무엇을 하려는가?
2. 그 목적을 쉽게 달성할 수 있는가?
3. 어디에서 망설이거나 막히거나 실수할 수 있는가?

## 3. 기준선 검사와 점수화

[사용성 평가 기준](references/usability-rubric.md)을 읽고 Clarity, Navigation, Feedback, Error Prevention, Forms, Accessibility, Responsive UX, Consistency, User Effort, States를 검사한다.

각 발견 사항에 다음 정보를 기록한다.

- ID와 관련 flow·화면
- 관찰 또는 재현 단계
- 사용자 영향과 근거
- 증거 유형: 사용자 관찰 / 실행 화면 / 코드 / 휴리스틱
- severity: Critical / High / Medium / Low
- 개선 권고와 검증 방법

각 기준을 0~10점으로 평가하고 기준선 총점을 계산한다. 해당하지 않는 기준은 `N/A`로 표시하고 나머지 항목으로 100점 환산한다. 증거가 부족하면 점수와 함께 신뢰도를 낮게 표시한다.

## 4. 문제 분류와 개선안 작성

발견 사항을 severity, 핵심 flow 영향, 수정 비용 순으로 정렬한다. 다음 내용을 포함한 최소 개선 묶음을 제시한다.

- 즉시 수정할 문제와 이유
- 변경할 화면·컴포넌트·상태
- 유지할 기존 패턴
- 기대 효과와 회귀 위험
- 수정 후 재검증할 시나리오

이 단계에서는 제품 코드를 수정하지 않는다. 코드 수준의 수정 지점을 확인할 수 있으면 관련 파일·컴포넌트와 변경 방향을 권고로 기록하되, 구현 완료로 표현하지 않는다.

## 5. 초기 REPORT 생성과 진행 확인

[HTML 템플릿](assets/UXUI.template.html)을 사용해 프로젝트 루트에 `REPORT-{yy-mm-dd}.html`을 생성한다. 날짜는 실행 환경의 현지 날짜를 기준으로 각각 두 자리 연·월·일을 사용한다. 예: 2026년 8월 21일은 `REPORT-26-08-21.html`이다.

초기 보고서에는 평가 목적과 방법, 핵심 flow, 항목별 기준선 점수와 시각화, 장점, 단점, severity별 문제, 개선 권고, 확인 가능한 코드 수준 수정 포인트를 포함한다. 개선 후 점수와 재검증 결과는 `미실시`로 명시하며 추정값을 넣지 않는다.

같은 날짜의 보고서가 이미 있으면 같은 평가의 기존 산출물인지 확인한다. 같은 평가이면 해당 파일을 이어서 업데이트하고, 다른 평가이거나 판단할 수 없으면 덮어쓰지 말고 사용자에게 알린다.

초기 보고서 경로와 Critical·High 문제를 요약해 제시하고, 어떤 개선안을 진행할지 사용자에게 확인한다. 사용자의 명시적 승인 전에는 다음 단계로 넘어가지 않는다.

## 6. 승인된 개선 구현

- Critical과 High 문제부터 근본 원인을 수정한다.
- 기존 컴포넌트, 토큰, 라우팅, 폼과 validation 체계를 재사용한다.
- 클릭·입력·단계를 줄이되 필요한 확인과 오류 예방을 제거하지 않는다.
- loading, empty, error, success, disabled, focus 상태를 빠뜨리지 않는다.
- keyboard, label, semantic 구조, 대비와 작은 화면 동작을 함께 수정한다.
- 사용자가 요청한 flow 밖의 리팩터링이나 시각 재설계는 별도 과제로 남긴다.
- 승인받은 항목만 구현한다. 코드 수정이 불가능하면 개선안을 구현 완료로 표시하지 않는다.

## 7. 동일 조건 재검증과 REPORT 업데이트

기준선과 같은 사용자, 목적, flow, 기기 조건으로 다시 검사한다.

- 수정한 문제의 재현 여부를 확인한다.
- 인접 flow와 상태의 회귀를 확인한다.
- 10개 기준을 다시 점수화한다.
- 개선 전후 차이를 근거와 함께 기록한다.
- 실행 검증을 하지 못했다면 코드 기반 추정이라고 표시하고 신뢰도를 낮춘다.

점수 상승보다 Critical·High 문제 해결과 핵심 목적 달성을 우선한다. 재검증하지 않은 항목에 임의의 개선 점수를 부여하지 않는다.

초기 평가에서 생성한 동일한 `REPORT-{yy-mm-dd}.html`을 업데이트한다. 새 최종 보고서를 별도 파일로 만들지 않는다. 보고서에 반드시 포함한다.

- 테스트 목적, 대상 사용자, 범위, 환경과 증거 방식
- 평가 항목과 평가 방법
- 핵심 flow와 성공 조건
- 개선 전·후 총점, 항목별 점수, 변화량과 신뢰도
- 항목별 점수를 비교할 수 있는 막대, 표 또는 그에 준하는 시각 요소. 수치를 함께 표기하고 색상만으로 차이를 전달하지 않는다.
- 확인된 장점, 단점과 개선 권고
- severity별 발견 사항과 근거
- 실제 적용한 개선과 관련 파일·컴포넌트·코드 수준 수정 포인트
- 접근성·반응형·상태 검증 결과
- 미해결 문제, 제한사항, 다음 권고

템플릿의 모든 `{{PLACEHOLDER}}`를 실제 값이나 HTML 조각으로 교체하고 남은 placeholder가 없는지 검사한다. 외부 CDN이나 원격 폰트 없이 단일 HTML로 유지하며, 상대 경로의 로컬 증거 이미지만 선택적으로 연결한다. 비밀정보와 개인정보는 포함하지 않는다. 파일을 자동으로 열지 않는다.

## 8. 완료 보고

한 줄 결과와 함께 다음만 보고한다.

- 개선한 핵심 flow와 가장 중요한 변경
- 해결된 Critical·High 문제 수
- 개선 전·후 점수와 검증 신뢰도
- 업데이트한 `REPORT-{yy-mm-dd}.html` 경로
- 남은 위험과 실행하지 못한 검증
