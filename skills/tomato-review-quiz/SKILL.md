# 변경사항 이해도 Review Quiz

현재 작업의 실제 코드 변경만 근거로 짧은 객관식 Quiz를 진행한다. 목적은 사용자의 이해를 돕고 확인하는 것이며, 코드 품질을 평가하거나 사용자를 시험하는 것이 아니다.

## 핵심 원칙

- 변경 목적, 핵심 로직, 데이터 흐름, 조건별 동작, 오류 처리와 영향 범위를 우선한다.
- 실제 diff와 변경 파일에서 확인할 수 없는 동작은 추측하거나 문제로 만들지 않는다.
- 사소한 문법, 줄 번호, 코드 스타일이나 암기성 세부사항은 묻지 않는다.
- 사용자가 이미 알고 있을 것이라고 가정하지 않되 함정 선택지나 불필요하게 어려운 표현을 사용하지 않는다.
- Quiz는 한 번에 한 문제만 출제하고 답변 직후 결과와 설명을 제공한다.
- Skip은 진행 중 언제든 허용한다.
- diff에 비밀키, 토큰, 개인정보가 있으면 문제, 설명, 보고서에 값을 노출하지 않는다.

## 1. 변경 범위 확정

Quiz 전에 현재 작업에 속한 변경 범위를 확정한다. 다음 순서로 근거를 선택한다.

1. 작업 시작 시 기록한 기준 commit 또는 명시된 비교 범위
2. 현재 작업에서 직접 수정한 파일 목록과 staged·unstaged diff
3. 사용자가 지정한 commit, branch 또는 diff 범위

untracked 파일은 일반 diff에서 빠질 수 있으므로 현재 작업에서 새로 만든 파일인지 확인하고 필요한 내용만 읽는다. 기존의 사용자 변경이나 다른 작업의 diff를 섞지 않는다. 작업 범위를 신뢰성 있게 구분할 수 없으면 추측하지 말고 비교 기준을 사용자에게 확인한다.

변경이 이미 commit된 경우 그 commit이 현재 작업의 결과라는 근거가 있을 때만 해당 commit diff를 사용한다. 검토할 변경이 없거나 diff를 확보하지 못하면 Quiz를 만들지 않는다.

## 2. diff 분석

변경 통계와 실제 diff를 함께 읽고 다음을 정리한다.

- 작업 목적과 사용자에게 보이는 동작 변화
- 수정·추가·삭제된 주요 파일과 역할
- 새로 추가되거나 변경된 핵심 로직
- 상태 관리, 데이터 흐름과 API 계약의 변화
- 비동기 처리, 오류·예외·복구 경로의 변화
- 공통 모듈, 호출자와 인접 기능에 대한 직접·간접 영향
- 변경 전후에도 그대로인 범위

생성 파일, lockfile, 포맷팅만 바뀐 줄은 복잡도와 문제 소재에서 비중을 낮춘다. 코드 품질상의 별도 결함을 발견해도 이번 변경의 이해에 필요하지 않으면 Quiz에 끼워 넣지 않는다.

## 3. 복잡도와 문제 수 결정

파일 수나 변경 줄 수만으로 결정하지 말고 동작 변화와 위험 신호를 함께 판단한다. 서로 다른 단계의 신호가 섞이면 더 높은 동작 복잡도를 우선한다.

| 복잡도 | 판단 기준 | 문제 수 |
| --- | --- | --- |
| 매우 간단 | 대체로 1개 파일과 10줄 안팎의 의미 있는 변경이며 동작 변화가 없거나 한 가지로 명확함 | 1 |
| 간단 | 대체로 1~2개 파일의 국소 로직 변경이며 상태·API·공통 모듈에 영향이 없음 | 1~2 |
| 보통 | 여러 파일에 걸친 새 로직, 상태나 데이터 흐름, validation 또는 예외 처리 변화가 있음 | 3~4 |
| 복잡 | API 인터페이스, 공통 모듈, 여러 계층, 비동기 흐름이나 복구 경로가 함께 바뀌어 영향 범위가 넓음 | 5~6 |

범위 안에서 독립적으로 이해해야 할 핵심 개념 수에 맞춰 문제 수를 고른다. 같은 개념을 문제 수를 채우기 위해 반복하지 않는다. 항상 최소 1개, 최대 6개로 제한한다.

## 4. 문제 설계

첫 문제를 보여주기 전에 전체 문제와 정답 근거를 준비한다. 각 문제는 다음 조건을 지킨다.

- 질문 하나에 핵심 개념 하나만 다룬다.
- 네 개의 선택지를 제공하고 정답은 하나만 둔다.
- 오답도 그럴듯하지만 실제 diff로 명확히 배제할 수 있어야 한다.
- 변경의 주요 목적, 전후 데이터 흐름, 추가된 함수나 조건의 이유, 오류 처리, 영향 범위 순으로 우선한다.
- 정답 설명에는 관련 파일·함수·조건 등 diff에서 확인한 근거를 간단히 포함한다.
- 코드 일부를 인용해야 하면 이해에 필요한 최소 부분만 사용하고 민감한 값은 가린다.

복잡도와 총 문제 수를 먼저 알리고 `skip`, `스킵`, `리뷰 생략`처럼 의사를 표현하면 언제든 건너뛸 수 있다고 짧게 안내한다.

## 5. Quiz 진행

문제는 `Q1`, `Q2` 순서로 한 개씩 제시하고 선택지는 `1`부터 `4`까지 표시한다. 번호나 선택지 문구로 답할 수 있게 한다.

정답이면:

1. 정답임을 즉시 알린다.
2. 변경 코드에 근거한 설명을 1~3문장으로 제공한다.
3. 남은 문제가 있으면 다음 문제 하나만 출제한다.

오답이면:

1. 오답임을 담담하게 알린다.
2. 변경 코드 기준으로 핵심 개념을 짧게 설명한다.
3. 같은 개념을 명확하게 다시 표현해 재출제한다. 필요하면 선택지 순서를 바꾼다.
4. 정답을 맞히기 전에는 다음 문제로 넘어가지 않는다.

재출제는 새로운 문제로 세지 않는다. 이미 맞힌 문제는 다시 묻지 않는다. 사용자가 질문하거나 대화를 잠시 전환해도 현재 문제와 통과 상태를 유지한다.

모든 원래 문제를 맞힌 경우에만 이해 확인 완료로 처리하고, 확인한 핵심 내용을 짧게 요약한다. 정상적으로 Quiz를 완료한 경우 `REVIEW.html`은 사용자가 요청할 때만 생성한다.

## 6. Skip 처리

사용자가 시간 부족, 나중에 확인, 문제 생략 등 Quiz를 건너뛰려는 의사를 표현하면 추가 확인 없이 Skip으로 처리한다. Skip은 실패가 아니며 작업 자체를 완료할 수 있다.

Skip 시에는 [REVIEW.html 템플릿](assets/REVIEW.template.html)을 사용해 프로젝트 루트에 `REVIEW.html`을 반드시 생성한 뒤 완료한다. 진행 중 Skip했다면 이미 답한 문제와 남은 문제를 모두 포함한다.

기존 `REVIEW.html`이 있으면 같은 작업의 문서인지 확인한다. 같은 작업이면 최신 diff 기준으로 갱신한다. 다른 작업의 문서이거나 판단할 수 없으면 임의로 덮어쓰지 말고 사용자에게 알린다.

## 7. REVIEW.html 작성

보고서는 외부 CDN, 원격 폰트와 외부 스크립트 없이 브라우저에서 바로 열리는 반응형 단일 HTML로 만든다. 필요한 최소 CSS를 문서에 포함하고 JavaScript는 꼭 필요할 때만 사용한다.

반드시 포함한다.

- 변경 요약: 작업 목적, 핵심 변경, 주요 파일과 범위
- Before / After: 동작 흐름을 Card, Flow 또는 Timeline으로 비교
- 핵심 코드: 전체 파일이 아닌 이해에 필요한 부분과 `무엇 / 왜 / 기존과의 차이`
- 영향 범위: 직접 영향, 간접 영향, 영향 없음을 구분한 Badge 또는 Card
- 주의 사항: 예외 상황, 의존 관계, 사이드 이펙트와 향후 수정 시 주의점
- 핵심 내용: 반드시 알아야 할 내용 3~5개
- Review Quiz: 원래 계획한 모든 문제, 선택지, 정답과 설명

Quiz 정답과 설명은 `<details>` 안에 두어 기본 상태에서 보이지 않게 한다. Before / After가 같거나 증거가 부족한 항목은 억지로 차이를 만들지 말고 `변경 없음` 또는 제한사항을 표시한다. 코드와 사용자 입력은 HTML escape하여 문서 구조나 스크립트로 해석되지 않게 한다.

템플릿의 모든 `{{PLACEHOLDER}}`를 실제 값 또는 HTML 조각으로 바꾸고 남은 placeholder가 없는지 확인한다. 자동으로 브라우저를 열지 않는다.

## 완료 조건

다음 중 하나를 충족해야 현재 작업의 이해 확인을 완료로 처리한다.

1. 사용자가 원래 문제를 모두 맞힘
2. 사용자가 Skip 의사를 밝혔고 현재 diff 기반의 `REVIEW.html` 생성이 완료됨

Quiz 근거가 될 변경 범위를 확보하지 못했거나, Skip 후 `REVIEW.html`을 생성하지 못했다면 완료로 처리하지 않고 필요한 정보나 해결할 장애를 명확히 알린다.
